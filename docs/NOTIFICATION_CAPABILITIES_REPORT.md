# Windows Notification Capture & API Feasibility Report

## 1. Executive Summary

During Phase 1 of the **Notify Hub** development, a rigorous technical investigation and empirical proof of concept were conducted on Windows 11 (OS Build 26300, 64-bit). The objective was to determine the precise capabilities, permissions, restrictions, and limitations of accessing Windows desktop notifications generated by third-party applications.

**Empirical Result:**  
Notification monitoring is fully functional using the native Windows WinRT `Windows.UI.Notifications.Management.UserNotificationListener` API. In direct testing, Notify Hub successfully detected, extracted, and recorded live toast notifications from installed applications, including **Slack**, **Antigravity**, **web browsers**, and **Windows system components**.

---

## 2. Windows Notification Architecture

Windows manages notifications through the **Windows Action Center / Notification Platform (WNP)**. To understand what Notify Hub can and cannot capture, applications can be classified into three architectural categories:

### A. Modern Toast Notifications (Fully Accessible)
Modern desktop applications generate notifications via the Windows Toast Notification platform. This includes:
- **Win32 Desktop Apps:** Modern Win32 applications that register an Application User Model ID (AUMID) and call `Windows.UI.Notifications.ToastNotificationManager` or standard Shell toast APIs. Examples: Slack, Microsoft Teams, Telegram Desktop, WhatsApp Desktop, Discord, Visual Studio, Spotify.
- **UWP & MSIX Packaged Apps:** Applications distributed via the Microsoft Store or MSIX packages. Examples: Windows Mail & Calendar, Phone Link, WhatsApp Store edition, Windows Security.
- **Web Browsers & Progressive Web Apps (PWAs):** Chrome, Microsoft Edge, Brave, and Firefox deliver web push notifications and PWA alerts directly into the Windows Notification platform.
- **Windows System Notifications:** Windows Defender alerts, Windows Update notices, battery notifications, hardware plug/unplug events.

**Captured Data:**
- **App Display Name:** (e.g., `"Slack"`, `"WhatsApp"`, `"Google Chrome"`)
- **Application Identifier (AUMID):** (e.g., `"Slack"`, `"Microsoft.SkypeApp_kzf8qxf38zg5c!App"`)
- **Notification ID:** Unique 32-bit unsigned integer per notification session
- **Creation Timestamp:** High-precision `DateTimeOffset`
- **Visual Text Elements:**
  - Text Element 0: Notification Title (e.g., sender name, channel, subject)
  - Text Elements 1..N: Notification Body, preview text, or multi-line details

## 3. The `UserNotificationListener` API

The primary, officially supported mechanism for monitoring notifications across applications is:
`Windows.UI.Notifications.Management.UserNotificationListener` (introduced in Windows 10 build 14393 and present in all modern Windows 10/11 editions).

### Permission & Authorization Lifecycle
1. **API Support Check:** `ApiInformation.IsTypePresent("Windows.UI.Notifications.Management.UserNotificationListener")`
2. **Access Status Query:** `UserNotificationListener.Current.GetAccessStatus()`
   The status returns one of three values:
   - `Allowed`: Full access granted. The application can query active notifications and subscribe to real-time events.
   - `Denied`: Access was explicitly blocked in Windows Privacy Settings.
   - `Unspecified`: User has not yet granted permission.
3. **Requesting Authorization:**
   Calling `await UserNotificationListener.Current.RequestAccessAsync()` prompts Windows to register the app or open the consent dialogue. If permission is ever revoked, the user can re-enable it under:
   `Windows Settings > Privacy & security > Notifications > Let apps access your notifications`.

## 4. Background Execution & Reliability Architecture

A key requirement of Notify Hub is continuous background monitoring without draining system resources or freezing the UI:

1. **Dual Capture Strategy (Event-Driven + Periodic Sync):**
   - **Real-Time Event:** `UserNotificationListener.Current.NotificationChanged += ...` fires immediately whenever Windows posts a toast notification (`UserNotificationChangedKind.Added`).
   - **Periodic Fallback Synchronization:** A lightweight timer polls `GetNotificationsAsync(NotificationKinds.Toast)` every 3.5 seconds. This guarantees that even if Windows drops an event during system sleep, hibernation, or high CPU spikes, no notification is ever lost.
2. **Deterministic Deduplication:**
   Windows notification IDs can repeat across reboots or across distinct applications. Notify Hub builds a composite unique key:
   `CompositeId = $"{AppId}_{UserNotificationId}_{CreationTimestampUtc}"`
   Deduplication occurs at two layers:
   - In-memory `HashSet<string>` for ultra-fast $O(1)$ lookups.
   - SQLite `UNIQUE INDEX` constraint (`UX_Notifications_NotificationId`) on the database table.
3. **Independent Background Lifecycle:**
   - The notification monitoring engine is decoupled from the WPF dashboard window.
   - Closing or minimizing the dashboard hides the window to the Windows System Tray (`System.Windows.Forms.NotifyIcon`).
   - The background service continues listening, categorizing, persisting, and forwarding without interruption.

## 5. Explicit Notification Limitations (What Cannot Be Captured)

While Notify Hub captures all standard Windows notifications, Windows enforces certain boundaries that must be documented:

| Scenario / App Type | Capture Feasibility | Technical Reason & Explanation |
|---|---|---|
| **Windows Toast Notifications** | **100% Captured** | Fully registered with Windows Notification Platform. |
| **Slack / Teams / WhatsApp / Telegram** | **100% Captured** | All use standard Windows Action Center toast notifications. |
| **Chrome / Edge / Firefox Push Notifications** | **100% Captured** | Delivered through Windows Action Center. |
| **Legacy Win32 Balloon Tooltips** | **Not Captured** | Deprecated Win32 `NIM_ADD` system tray balloon popups do not generate `UserNotification` toast records. |
| **Custom In-App Direct-Drawn Overlays** | **Not Captured** | Applications (such as some PC games or legacy trading terminals) that render their own top-level borderless DirectX/GDI windows on screen bypass the Windows notification platform entirely. |
| **Focus Assist / Do Not Disturb** | **Captured upon delivery** | When Focus Assist is enabled, Windows silences the banner sound/popup but still posts the notification into Action Center, where Notify Hub captures it. |
| **Permission Denied in Windows Settings** | **Blocked by OS** | If the user toggles "Notification Access" OFF in Windows Privacy Settings, the OS returns `Denied` and blocks third-party listener access. |

---

## 6. Phase 1 Feasibility Conclusion

The feasibility investigation confirms that:
1. `UserNotificationListener` is active, allowed, and reliable on Windows 10 and 11.
2. Third-party notifications from productivity apps, communication tools, and system services are completely accessible.
3. Notify Hub does not need to simulate or mock notifications; all capabilities operate on real Windows system APIs.
